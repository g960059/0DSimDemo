結論から述べます。Standard71で作られた「凍結JSON＋説明文＋描画TSX」の形は方向として正しいものの、現状はまだ版固有のTSXと生きた実行コードに縛られていて、Standard72以降で同じ作り方を繰り返すと保守も退役もできません。私の提案は、版ごとに「モデル文書パッケージ」を一つの自己完結JSONとして鋳造時に凍結し、描画は版非依存の一つのTSXに寄せ、実行コードは最新と一つ前だけを残す、という構成です。以下、事実と提案を分けます。

## 確認できた事実

**文書ページの実装は二世代が同居している。**

- 66/67と68/69/70のページは、TSX内の文言表と「facts」解決器で作られ、解決器はclient.json・Surface・検証報告・出力カタログといった実行系の生きたコードを読みます。実行コードを消すとこれらのページは壊れます。
- 71のページは二つの凍結JSONを読みます。基線評価と設定を持つ文書スナップショットと、回路・係数・初期状態を持つ数式データです。数値の権威は保存記録側にあり、ページは生成器で再作成される設計です。
- 71の生成器は、fixture工場を直接importし、採択記録と構成が一致しない場合は生成を拒否します。数式データ生成器は実行コード29ファイルと起動チェックポイントのSHA-256を記録し、vitestがその一致を生木に対して検査します。したがって72で該当エンジンファイルを一つでも変更すると、71の文書試験は失敗します。これは「文書が版のコードに縛られている」ことを意味します。
- 文書スナップショットの来歴は `artifacts/` 配下のパスを指しますが、そのディレクトリはgitignoreされています。71の来歴にはコミットハッシュもありません。70の起動基線JSONにはexecutionCommitがあります。

**71のTSXはまだ汎用描画器ではない。** 版固有の文言が描画コードに直書きされています。

| 直書き箇所 | 内容 |
| --- | --- |
| 見出し・題名 | 「Main Wire Standard 71」、ローカル候補の状態文 |
| 評価要約 | 「PAP拡張期値、LVの等容期・Tei・dP/dtには逸脱が残る」 |
| 検証記録の選択肢 | 「2 ms · Standard71独立再実行と一致」 |
| 予備能の限界 | 「低容量側RV経壁圧に約7%の刻み差」 |
| 変更履歴 | Standard70からの差分の文章 |
| 材料係数の意味 | 日本語のみの辞書、英語は無い |
| 制御ラベル | 心膜・冠動脈の正規表現による特例 |

**「モジュール」の説明文は版非依存ではない。** 数式仕様の散文にτrec、β、γ、Lの固定点、受動則の倍率、動脈Vsの換算倍率、抵抗倍率、χmin、kmax、pなどの数値が埋め込まれています。弁モジュールの本文には「Standard71には圧回復補正がない」と版名も入っています。モジュールIDの版接尾辞は手動で、exact manifestが持つprofile IDとは結び付いていません。

**版と実行コード。** 65から71まで七つの識別子が同居し、fixture工場・checkpoint codec・typed session・出力レジストリが版ごとに存在します。66版のexact model TSは71までの変種をunionとinstanceof分岐で抱えています。dev用の組成ファイルには版ごとに複製されたローダーが並びます。65は文書ページを持たず、Model Labからのみ到達できます。AGENTS.mdは「旧識別子はretire」と定めていますが、実態は全版保持です。

**実行の必要物。** artifact.mjsは自己完結ESMで、検証ツールが外部importを禁じています。ブラウザ側が必要とするのはmanifest・fixture投影・Surface・pinされた解析法の実装だけで、fixture投影は66から71まで同一、解析法はv8とv9が両方残っています。つまり、版のエンジン源を消しても、artifactと付随JSONが残れば再実行はできる設計です。Supabase側にはartifact・manifest・Surfaceは保存されますが、文書は保存されません。文書はクライアントのビルドにしか存在しません。

**registryとpreset。**

- 正常参照エビデンス登録簿は20グループで、うち8つは参考警告です。文書スナップショットはこの登録簿を丸ごと複製して凍結します。gate来歴はgateごとに passage-checked な一次資料か、リポジトリ内の仕様と回帰試験への参照を要求します。
- fitting参照登録簿の唯一の項目「baseline」は今もStandard70の起動基線に束縛され、71への切替は未実施です。起動基線の検証器は70の候補入力値を直書きしています。
- 「preset」という語は現在、機械的補助のデバイス設定にしか使われていません。病態presetの登録簿は存在しません。CALIBRATION文書は「presetはSurfaceに露出した表現型だけを変える。内部変更が要るならモデルを鋳造する」と定めています。
- 文書の解決は exact model と Surface release の対で行い、別releaseでの代用を拒否します。同一Surface系列の追加releaseでも「文書なし」になります。

## 提案：モデル文書パッケージと三層の版管理

**基本方針。** 文書は「鋳造時に凍結する成果物」であり、「生きたコードから毎回導く投影」ではない。Standard71がJSONでやりかけたことを最後まで進め、散文・ラベル・限界の一覧までパッケージに入れて自己完結させます。描画TSXは一つだけにし、版ごとのTSXは作りません。実行コードは最新と一つ前だけを残し、それより古い版は「パッケージ＋artifact」で生き残ります。

**パッケージの中身。** 一版につき一つのJSONで、次を持ちます。

- 識別: modelId、surfaceSeriesId、作成時のsurfaceReleaseId、baselineId、鋳造コミットのハッシュとgitタグ名。
- 機構節: exact manifestとfixture claimのprofile IDをキーにした節の配列。各節に要約・詳細・数式・記号表・係数表・出典を両言語で持つ。散文は鋳造時に草稿ライブラリから複製し、以後は変更しない。
- 組み立てと初期条件: 現在の数式データJSONの内容。
- 基線: 現在の文書スナップショットの内容に、日本語の根拠文と範囲ラベルの訳語を含めて凍結する。今はコード内の正規表現で訳しているものです。
- 制御と出力のラベルと説明: 鋳造時にSurfaceと提示カタログから複製する。
- この版の変更点: profile IDの差分を機械的に列挙した表と、手書きの一段落。
- 限界の一覧とバッジ表記: 今は翻訳JSONに版ごとに散っているものをここへ移す。
- 来歴: 参照した実行コードのSHA-256、エビデンス登録簿のSHA-256、成果物パス。これは記録であり、試験の主張ではない。

**描画と試験。** 描画TSXは版名を一切知らず、パッケージの節構造を辿って描くだけにします。一段の折りたたみと固定の章立てはそのまま維持します。試験は二種類に分けます。

- 鋳造時試験: 現行候補のみを対象に、文書の数式と実行コードの一致を再構成で検証する。今の71試験の後半がこれで、版のコードと一緒に退役する使い捨てです。
- 恒久試験: 全パッケージを対象に、スキーマ妥当性、体積総和とTBVの一致、両言語で数値と判定が同一、KaTeXエラー無し、入れ子無し、散文に係数値が混入していないことを検査する。この試験は実行コードを一切importしない。

**モジュール性の扱い。** 再利用は「執筆時」に限り、「表示時」には行いません。草稿ライブラリはprofile IDで引ける節の集まりとしてリポジトリに置き、鋳造時に該当節を複製します。同じprofile IDなら散文は同じ、変われば新しい節を書く、という単純な規則です。散文には数値を書かず、値は表から描く。表示時に共有ライブラリを読む方式は、古い版の説明を後から書き換えてしまう上、今回のように版固有の数値が混ざるので採りません。

**版管理の階層。**

| 階層 | 置き場所 | 中身 | 再実行 | 文書 |
| --- | --- | --- | --- | --- |
| 研究候補 | worktree、artifacts/ | 実行コード、評価記録 | 可 | 未作成 |
| ローカル採択 | main、gitタグ | 実行コード、artifact、client.json、checkpoint、パッケージ | dev組成で可 | 可 |
| 登録済 | Supabase registry | artifact、manifest、Surface | 任意のクライアントから可 | クライアントに同梱 |
| 退役 | main | パッケージのみ。artifactは保存内容が参照する場合だけ残す | タグをcheckout | 可 |

実行コードの保持規則は「現行と一つ前」です。72を採択したら70の源を消し、73を採択したら71の源を消します。71は当面、artifactとclient.jsonをコミットして「ローカル採択」に上げるのが先です。今の71は源だけがあり、artifactが木に無いので、退役の準備ができていません。

**presetと他のregistry。** presetを「Surfaceに露出した制御値の組＋来歴＋その版での評価記録」として一つのスキーマで扱い、baselineをその最初の項目にします。

- 定義は版をまたいで複製できるが、評価記録は版ごとに作り直す。CALIBRATION文書の「後継は新しいfitting対象」に一致します。72鋳造時には全presetを再評価する一つのコマンドを用意し、未評価のpresetはページ上で未評価と表示します。
- gateの来歴要件は役割で分ける。baselineは今の passage-checked 方式のまま。病態presetは「表現型を定義する観測」に最低一つの一次資料と所在を要求し、数値品質検査は常に必須、その他の範囲は参考扱いに留める。全検査に文献範囲を求めると、HFpEFのように良い一次資料が薄い病態でpresetが作れなくなります。
- 個別デモのfittingはregistry項目にしない。既存のExperiment/Snapshotに評価報告を添付する形にし、公開一次資料由来の症例だけをpresetへ昇格させる。実データはローカルに留める既存の境界を守ります。
- fitting参照登録簿の「baseline」は71採択時に明示的に付け替える。fallbackは今後も作らない。
- エビデンス登録簿はsourceIdごとに追記のみとし、範囲の変更は新しいsourceIdか新しい登録簿IDで行う。パッケージが登録簿を複製して凍結する現在の方式は維持します。

**文書とSurfaceの束縛。** 対の一致からSurface系列の一致に緩めます。系列内では定義の変更が禁じられ追加しかできない設計なので、ラベルの意味は保たれます。パッケージには作成時のreleaseを記録し、より新しいreleaseで開かれたときは注記を出せば足ります。

**workbenchとの共有。** 制御・出力・graph項目の説明は提示カタログを唯一の執筆元とし、workbenchは生きたカタログを、文書は鋳造時の複製を使います。パッケージが自己完結する代償として重複しますが、Surface系列が消えても文書が描けることを優先します。

## 移行手順・やらないこと・弱点

**手順。**

1. 71を「ローカル採択」に上げる。artifactとclient.jsonをコミットし、タグを打ち、来歴にコミットハッシュを入れる。72の作業前に済ませる。
2. パッケージのスキーマを定め、71の二つのJSONと散文・ラベル・限界一覧・翻訳JSONの版固有項目を一つに束ねる変換器を書く。71のTSXから版固有の直書きを全て抜き、パッケージだけを読む描画器にする。試験を鋳造時と恒久の二つに分ける。
3. 66から69の描画TSX、facts解決器、翻訳項目、文書登録項目を退役させる。70は登録済の既定モデルなので、源が残っているうちに70用の抽出器を一度だけ動かしてパッケージを作る。68と69は同じ世代なので作るなら同時、作らないならgit履歴に任せる。
4. 72鋳造時は71の抽出器を複製して72用にし、パッケージを生成する。71のパッケージには触れない。70の源、typed session、組成ローダー、unionの分岐を削除する。
5. presetスキーマと再評価コマンドを導入し、baselineを最初のpresetにする。病態presetはその後に足す。
6. 73鋳造時に71の源を削除する。artifactは保存内容やregistryの参照が無ければ一緒に消す。

**やらないこと。**

- 版ごとの描画TSXや版ごとのfacts解決器を新たに書かない。
- 文書をSupabaseに保存しない。文書はクライアント同梱で足りる。
- 表示時に共有散文ライブラリを読まない。古い版の説明を後から変えない。
- 後継モデルに文書やpreset評価を自動継承させない。
- 全ての歴代モデルをdev組成で動かし続けない。
- 文書スナップショットを第二の実行モデルにしない。これは現行の注記どおり。
- Markdown変換やCMSのような別経路を作らない。

**現行の方針・実装からの明示的な変更点。**

- 文書の解決を exact model と Surface release の対から、exact model と Surface 系列の対に緩める。
- 71の文書試験が実行コードのSHA一致を主張している部分を「来歴の記録」に格下げし、恒久試験から外す。
- リポジトリ衛生検査が65と66のartifactパスを必須にしている規則を見直す。退役でこれらは消えるため。
- 翻訳JSONに散っている版ごとの限界一覧をパッケージに移す。
- fitting参照登録簿の束縛先を70から71へ明示的に切り替える。

**弱点と未解決点。**

- パッケージのスキーマは必ず進化する。描画器が古いスキーマも読めるようにするか、パッケージを移行スクリプトで書き換えるかを決める必要がある。パッケージが二つか三つのうちは後者で足りるが、規律が要る。
- 散文は版間で重複し、誤字修正は古いパッケージに自動で届かない。散文フィールドだけを書き換えるスクリプトを許すなら、数値と評価フィールドは絶対に触らないという線引きを試験で守らせる必要がある。
- 「散文に数値を書かない」検査は発見的で、単位や年号との区別が難しい。許可リストが要る。
- 文書と実行コードの一致は鋳造時点の記録でしか保証されない。読者が後から再検証するにはタグをcheckoutするしかない。公開前の一人開発ではこれで足りると判断しますが、公開後に外部研究者へ「再現できる」と言うなら、artifactに対する検証手段が別途要ります。
- preset再評価は版ごとに定常化と予備能の計算を全presetで繰り返すため、preset数に比例して時間がかかる。件数が十を超える前に計算コストを測るべきです。
- 古いartifactを消す前に、registryとローカル保存内容がそのmodelIdを参照していないことを確認する手段が必要で、今回は確認していません。
- 70のパッケージを作るには70用の抽出器と、70の起動基線JSONを新スキーマへ写す変換が要る。この一回限りの作業量は中程度で、やらない選択も合理的です。
- 英語側の散文は日本語より薄い箇所がある。パッケージは両言語必須にすべきで、その執筆が71分だけでも残作業になります。
